PHASE 2 — PHONE-VS-FLIGHT-CONTROLLER SENSOR CROSS-CHECK
================================================================

WHAT & WHY
------------
This is your "no AI guesswork, just physics" safety story, and it's
one of the two things worth demoing live on stage. The phone has its
own GPS, accelerometer, and magnetometer — completely independent of
the flight controller's own sensors. If the two ever disagree beyond
a sane threshold (flight controller says level and stable, phone says
tilting and drifting), that's a real fault signal: a spoofed GPS
signal, a corrupted sensor, tampering, or a hardware fault. This
reuses the SAME underlying idea as AXIOM's behavioral-drift detection
(comparing an expected pattern against an observed one and scoring
the deviation), just grounded in raw physical sensors instead of
transaction/behavior data.

Important nuance to keep in the code and the pitch: the phone's
magnetometer is only trustworthy as a CROSS-CHECK, not a primary
source, if it's mounted anywhere near motors/ESCs (electromagnetic
interference throws it off). Build the comparison logic to account
for this, or exclude magnetometer-vs-magnetometer checks entirely and
lean on GPS + accelerometer/gyro comparisons as your primary fault
signal.

THINGS TO DO
--------------
- Read the phone's own GPS, accelerometer, and magnetometer via
  Android's SensorManager APIs, at a steady sample rate
- Read the flight controller's equivalent values from the MAVLink
  stream already flowing in Phase 1
- Write a comparison function: define a sane disagreement threshold
  for each sensor pair (e.g., position disagreement beyond X metres,
  attitude/tilt disagreement beyond Y degrees)
- When disagreement exceeds threshold, emit a clearly tagged "FAULT"
  message using the bridge app's existing prefix-routing pattern (the
  same pattern used for "US:" ultrasonic data — add a new prefix, e.g.
  "FAULT:", rather than inventing a whole new protocol)
- Send that FAULT message over the same Tailscale link from Phase 1 to
  the ground dashboard
- Build a simple way to MANUALLY trigger a fake disagreement for
  demo purposes (e.g., a debug button that injects a fake GPS jump),
  so you can reliably show the fault-detection working live without
  needing an actual hardware fault

REUSABLE COMPONENTS TO PLACE IN WORKSPACE
--------------------------------------------
- The existing "US:" prefix-routing pattern from the bridge app — copy
  its exact structure for the new "FAULT:" and "AI:" prefixes so the
  whole system stays consistent
- AXIOM's drift-detection scoring logic/math (even if written for a
  different domain originally) — reuse the actual thresholding/scoring
  approach, adapted to sensor values instead of transaction behavior

PHASE 5 — CERTIFIED 3D RECONSTRUCTION (COLMAP + MARKER SCALE)
================================================================

WHAT & WHY
------------
This is the "proof" layer, and it's the highest-technical-risk piece,
so read this section carefully before building.

Important correction to keep in mind: the actual MEASURED geometry
does not come from the pretty-looking 3D splat/model — it comes from
COLMAP, the step that runs BEFORE the pretty rendering. COLMAP does
structure-from-motion: it matches shared features across your
overlapping photos and triangulates a 3D point cloud plus camera
positions, with a measurable error value for how precise each point
is. That point cloud, not the rendered splat, is your actual ruler.
The splat (via gsplat/Nerfstudio) is a nice-looking, walkable render
built on top of it afterward — good for the "wow" demo, not for the
certified number.

The other missing piece is SCALE. A camera-only reconstruction knows
relative distances (point A is some multiple of the distance to point
B) but has no idea if that multiple means centimetres or metres. A
printed marker (ArUco/AprilTag) of a known, exact real-world size,
placed somewhere visible in the photos, fixes this: detect the
marker's corners in the reconstruction, compare its reconstructed size
to its real size, and that ratio becomes your scale factor. Multiply
every other distance in the point cloud by that factor and you have
real-world centimetres, with a stated margin of error — not
millimetre-perfect, but genuinely calibrated and defensible.

THINGS TO DO
--------------
- Print a physical ArUco or AprilTag marker at an exact, known size
  (measure it precisely with calipers/ruler, don't trust the printer)
- Capture a systematic, overlapping photo set of a real test area (a
  wall, a small structure — doesn't need to be an actual lake for the
  POC) with the marker clearly visible in at least 2 photos, camera
  settings (focus/exposure) LOCKED for the whole capture pass
- Run COLMAP on the photo set to get a sparse point cloud, camera
  poses, and per-point reprojection error
- Write a small script to detect the marker in the reconstruction,
  compute the scale factor against its known real-world size, and
  apply that factor to the whole point cloud
- Build a simple "pick two points, get a distance + margin of error"
  tool on top of the scaled point ccloud — this is your actual
  certified-measurement demo, and it does NOT require the pretty splat
  to be finished or even started
- Separately (lower priority, purely visual), feed the same photo set
  into gsplat/Nerfstudio to produce a walkable splat for the "wow"
  visual — but do not measure from it, and do not block the
  measurement demo on this finishing

PHASE 6 — TRUST LEDGER / TAMPER-PROOF HASH-ANCHORING

idea so a single faulty device or single bad actor can't fabricate a
result alone. For the POC, the on-chain anchoring can be simplified —
what matters for the demo is showing that ANY change to the underlying
data changes the hash completely and obviously, proving tampering
would be detectable.

software, has zero flight risk, and it's the part that visually sells

manageable days.

Note: this planner GENERATES the flight plan and shows it visually.
